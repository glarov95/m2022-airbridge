# M2022 AirBridge — Initial Engineering Specification

**Status:** Initial research/design handoff  
**Date:** 2026-08-31  
**Primary target:** macOS host + Samsung Xpress SL-M2022 connected over USB  
**Primary client:** iPhone/iPad on the same home LAN  
**Long-term direction:** Replace the legacy Samsung rendering path with our own maintained SPL/QPDL driver and optional improved rasterization.

---

## 1. Executive summary

Build a small macOS service that turns a USB-only Samsung Xpress SL-M2022 into a modern, discoverable AirPrint-compatible network printer.

The project should be delivered in two deliberately separate layers:

1. **AirPrint bridge first**
   - Keep using the already-working Samsung/macOS print queue.
   - Let macOS CUPS continue to talk to the physical printer over USB.
   - Expose the queue to iPhone/iPad using IPP + Bonjour/DNS-SD in the shape expected by AirPrint clients.
   - Make this reliable across reboot, sleep/wake, printer disconnect/reconnect, and Mac network changes.

2. **Own driver later**
   - Replace the proprietary/legacy Samsung rendering path with our own renderer + Samsung SPL/QPDL encoder.
   - Use OpenPrinting SpliX and its SPL2/QPDL documentation as protocol/reference material.
   - Eventually remove the dependency on the old Samsung driver entirely.
   - After correctness is established, experiment with higher-quality rasterization, grayscale/halftoning, text rendering, toner-density controls, and 600/1200 dpi profiles.

The critical architectural decision is **not to write a complete AirPrint/IPP stack or a complete Samsung driver at the same time**. The first useful version should be small and testable.

# 2. Known hardware facts

Target printer is assumed to be:

**Samsung Xpress SL-M2022**

Samsung's published specifications for the SL-M2022 state:

- Host interface: **Hi-Speed USB 2.0**
- Printer language/emulation: **SPL (Samsung Printer Language)**
- Maximum resolution: **up to 1200 × 1200 dpi**
- Monochrome laser
- Up to **20 ppm A4**
- 128 MB memory
- Manual duplex support
- 150-sheet input tray
- Original platform support was from the OS X 10.5–10.9 era.

This is the non-W model, so the design must assume **no useful built-in network interface**.

### Important verification

Before implementation, do not trust the model assumption blindly. The bootstrap probe must record:

- exact USB product string;
- exact USB Vendor ID / Product ID;
- configured macOS CUPS queue name;
- queue device URI;
- installed PPD/driver/filter paths;
- document formats currently accepted by the queue;
- macOS version;
- current CUPS version;
- current Mac architecture.

# 3. Research conclusions

## 3.1 IPP + DNS-SD is the correct network-facing interface

Modern driverless printing uses IPP and DNS-SD/Bonjour discovery.

The Printer Working Group's IPP Everywhere architecture requires an IPP service plus DNS-SD discovery and standard page formats. AirPrint uses a closely related model.

We should therefore expose a standards-shaped network printer rather than inventing a custom iPhone app or custom network protocol.

## 3.2 Do not create a new legacy CUPS printer driver as the long-term architecture

Classic CUPS PPD/filter/backend printer drivers are deprecated.

OpenPrinting recommends **Printer Applications** for old printers that still need hardware-specific code. A Printer Application appears to clients as a modern IPP printer while internally translating into the legacy printer's native format.

This is exactly the long-term model we want.

## 3.3 PAPPL is the preferred long-term IPP framework

PAPPL is an actively maintained C framework specifically designed for Printer Applications.

Relevant properties:

- IPP Everywhere service
- DNS-SD/mDNS integration
- macOS support
- Apple Silicon development/testing
- USB and network device support
- PWG Raster and Apple Raster support
- spooling, jobs, status, web interface, discovery
- designed as the replacement architecture for legacy drivers

Therefore, if/when we stop leaning on macOS's built-in CUPS server, the direct-driver version should strongly prefer PAPPL over a hand-written IPP implementation.

## 3.4 SpliX is highly relevant to the M2022

OpenPrinting's SpliX project implements Samsung SPL2/QPDL printing and explicitly lists **Samsung M2020 Series** among its supported models.

The current code also contains M2020-series-specific behavior (`specialBandWidth`) and emits QPDL.

SpliX's current implementation uses CUPS raster input and includes compression support including JBIG85.

This gives us three choices for the direct-driver stage:

### Option A — Use/fork SpliX code
Fastest route to direct SPL output.

Downside:
- SpliX is GPL-2.0 licensed.
- A distributed derivative would need to respect GPL obligations.

### Option B — Treat SpliX as an external executable
Our app creates raster data and invokes a SpliX-derived filter as a separate process.

This may simplify boundaries, but licensing still needs to be handled correctly for packaging/distribution.

### Option C — Clean implementation from documented SPL2/QPDL behavior
Use public protocol documentation and captured test fixtures to build our own encoder.

This is the best long-term engineering shape if we want a permissively licensed standalone project, but it is slower.

**Initial recommendation:** for a private/personal project, prototype with SpliX as the reference/oracle first. Decide licensing strategy before publishing.

# 4. Product goal

From an iPhone on the same Wi-Fi:

1. Open a PDF, web page, photo, note, email attachment, etc.
2. Tap **Share → Print**.
3. See a printer called something like:
   - `Samsung M2022`
   - or `M2022 AirBridge`
4. Select it.
5. Print normally.
6. The job travels over Wi-Fi to the Mac.
7. The Mac sends it over USB to the Samsung.
8. No custom iOS application is required.

The Mac is the print server.

---

# 5. Non-goals for the first working version

The first milestone must **not** attempt all of these:

- no custom SPL encoder;
- no direct libusb access;
- no replacement of the Samsung driver;
- no custom PDF renderer;
- no print-quality optimization;
- no toner-level reverse engineering;
- no iOS app;
- no cloud printing;
- no remote printing across the public Internet;
- no complex UI;
- no printer firmware modification.

The first milestone is successful when an iPhone can reliably print through the existing macOS queue.

# 6. Architecture overview

## Stage A — AirPrint bridge using the existing macOS queue

```text
┌──────────────┐
│ iPhone/iPad  │
└──────┬───────┘
       │ Wi-Fi
       │ Bonjour / DNS-SD discovery
       │ IPP print job
       ▼
┌───────────────────────────┐
│ Mac                       │
│                           │
│  M2022 AirBridge          │
│   - setup/validation      │
│   - Bonjour advertisement │
│   - health monitoring     │
│                           │
│  macOS CUPS               │
│   - IPP endpoint          │
│   - Samsung queue         │
│   - existing driver       │
└────────────┬──────────────┘
             │ USB
             ▼
      ┌──────────────┐
      │ Samsung      │
      │ SL-M2022     │
      └──────────────┘
```

Important point:

**AirBridge v0 does not need to own the IPP request-processing stack if the existing CUPS server can expose the queue correctly.**

The daemon's job is primarily to:

- discover the correct local queue;
- verify it is shareable;
- make sure CUPS allows LAN printing;
- register the appropriate Bonjour/DNS-SD service;
- expose diagnostics;
- keep the advertisement valid as interfaces change;
- optionally repair configuration after OS updates/reboots.

This is the lowest-risk vertical slice.

# 7. Stage A protocol plan

## 7.1 CUPS side

CUPS already supports printer sharing via IPP.

The intended queue endpoint is conceptually:

```text
ipp://<mac-hostname>.local:631/printers/<queue-name>
```

Setup should use the normal CUPS sharing mechanism rather than patching configuration files blindly.

Equivalent CUPS concepts:

```text
cupsctl --share-printers
lpadmin -p <queue> -o printer-is-shared=true
```

The setup code should **inspect first, mutate second**.

Default security posture:

- local subnet only;
- no Internet exposure;
- no `--remote-any` unless the user explicitly requests it;
- no printer administration remotely;
- printing only.

## 7.2 Bonjour / DNS-SD side

iOS discovers printers through Bonjour.

Historically, making a CUPS queue visible as AirPrint has involved advertising:

- `_ipp._tcp`
- `_universal._sub._ipp._tcp`

with TXT records describing the queue and accepted page description formats.

Useful TXT fields include:

```text
txtvers=1
qtotal=1
rp=printers/<queue-name>
ty=Samsung Xpress SL-M2022
note=USB printer via Mac
product=(Samsung Xpress SL-M2022)
Color=F
Duplex=F
Copies=T
priority=0
pdl=...
URF=...
```

**Do not hard-code a large PDL list.**

At runtime:

1. query the CUPS queue for supported document formats;
2. construct the advertisement from formats we can actually handle;
3. always validate with a real iPhone.

Historical AirPrint bridges advertise `application/pdf` and `image/urf` and include a `URF` TXT key. Modern behavior must be tested rather than assumed.

## 7.3 First proof-of-concept

The first proof-of-concept can be intentionally crude:

1. enable CUPS queue sharing;
2. run a foreground program that registers the Bonjour service;
3. verify the printer appears on the iPhone;
4. print a one-page PDF from Files.

Do not write launchd integration until this works.

# 8. Critical unknown: what job format will iOS actually submit?

This is the most important early experiment.

The CUPS queue may advertise/support several input MIME types.

Possible iOS job formats include:

- `application/pdf`
- `image/urf` / Apple Raster
- PWG Raster depending on implementation/path

For v0, the easiest outcome is:

```text
iPhone → PDF → CUPS → existing Samsung driver → SPL → USB
```

If iOS insists on Apple Raster/URF and the system queue cannot convert it, we have several fallback paths:

### Fallback 1
Add a conversion layer:

```text
URF/Apple Raster → PDF or CUPS/PWG Raster → existing Samsung queue
```

### Fallback 2
Use PAPPL as the network-facing server, because PAPPL already understands Apple/PWG Raster.

### Fallback 3
Move earlier than planned to our own raster pipeline and SPL output.

**Milestone 0 must capture the received document format rather than guessing.**

# 9. Recommended implementation stages

## Milestone 0 — Environment probe

**Goal:** Learn exactly what is installed on this Mac and how the current successful print path works.

Create:

```text
scripts/probe-macos.sh
```

It should capture sanitized diagnostic output into:

```text
artifacts/probe/YYYYMMDD-HHMMSS/
```

Suggested commands/data:

```bash
sw_vers
uname -a
uname -m

lpstat -p
lpstat -d
lpstat -v
lpoptions -l

ioreg -p IOUSB -l -w 0

ls -la /etc/cups
ls -la /etc/cups/ppd 2>/dev/null || true
ls -la /Library/Printers 2>/dev/null || true
```

For every queue, query IPP attributes if practical:

- `printer-make-and-model`
- `printer-info`
- `device-uri`
- `document-format-supported`
- `media-supported`
- `printer-resolution-supported`
- `sides-supported`
- `printer-state`
- `printer-state-reasons`

Also inspect the PPD for the target queue if present.

### Acceptance criteria

We know:

- exact queue name;
- exact device URI;
- exact driver/filter chain;
- exact USB VID/PID;
- whether the queue is already shared;
- whether local cupsd listens beyond localhost;
- document formats accepted by the queue.

## Milestone 1 — Manual AirPrint proof-of-concept

**Goal:** Print from iPhone without installing anything on iPhone.

No daemon yet.

Implement a tiny command:

```text
m2022-airbridge advertise --queue <queue>
```

Responsibilities:

- connect to local CUPS;
- load queue metadata;
- register an `_ipp._tcp` Bonjour service;
- add `_universal` subtype;
- build TXT records;
- remain foreground until Ctrl-C;
- log registration details.

For first iteration it may call the platform `dns-sd` utility, but production code should use the DNS-SD API directly.

### Acceptance tests

From iPhone:

- printer appears in the Print chooser;
- name and description are sensible;
- one-page PDF prints;
- multi-page PDF prints;
- Safari/web page prints;
- one JPEG/photo prints;
- canceling a job does not wedge future jobs.

---

## Milestone 2 — Reproducible installer + launchd

**Goal:** AirBridge survives reboot.

Add:

```text
m2022-airbridge install
m2022-airbridge uninstall
m2022-airbridge status
m2022-airbridge doctor
```

Installer responsibilities:

- locate/choose the Samsung queue;
- verify physical USB printer;
- enable sharing only if needed;
- configure minimal CUPS LAN access;
- install launchd service;
- start service;
- perform self-check;
- print clear rollback instructions.

Prefer one privileged setup step and an unprivileged runtime where possible.

### Runtime responsibilities

- register Bonjour service;
- observe interface changes;
- recover after sleep/wake;
- recover after printer disconnect/reconnect;
- re-register after hostname/network change;
- emit structured logs;
- never silently modify CUPS settings after install unless explicitly designed to do so.

# 11. Direct-driver investigation plan

## 11.1 Use SpliX as an oracle/reference

SpliX currently supports the Samsung M2020 Series.

Relevant parts to study:

- QPDL job setup;
- PJL header/footer;
- QPDL version used by M2020 family;
- M2020-specific band-width behavior;
- paper size encoding;
- resolution encoding;
- page-band framing;
- compression selection;
- JBIG85 path;
- manual duplex behavior;
- printer-specific PPD attributes.

Do not immediately refactor or copy everything.

First build fixtures.

## 11.2 Generate known-good SPL/QPDL fixtures

Create deterministic test pages:

```text
fixtures/pages/
  blank-a4.pdf
  black-square-a4.pdf
  horizontal-lines.pdf
  vertical-lines.pdf
  checkerboard.pdf
  gray-ramp.pdf
  small-text.pdf
  unicode-text.pdf
  photo.pdf
```

For each supported mode:

```text
600x600
1200x1200
A4
Letter
toner-save if available
normal/high quality
```

Generate expected Samsung/SpliX native output:

```text
fixtures/qpdl/
```

Then our encoder can be tested byte-wise or structurally.

## 11.3 Capture current proprietary driver output

If macOS still exposes the vendor filter/PPD chain, use CUPS tooling to render a test input to the printer-specific output without physically sending it.

Potential tool:

```text
cupsfilter
```

CUPS supports converting a document through a configured filter chain to `printer/foo`.

Exact invocation depends on the installed queue/PPD and must be discovered by Milestone 0.

This gives us a second oracle:

```text
input PDF
  ├── old Samsung driver → captured SPL
  └── SpliX             → captured QPDL
```

Compare both.

We do not need binary identity. We need to understand:

- headers;
- page framing;
- resolution;
- paper size;
- band dimensions;
- compression;
- end-of-job behavior.

# 12. SPL/QPDL encoder module boundary

Create a narrow API.

Pseudo-interface:

```c
typedef struct {
    int width_px;
    int height_px;
    int x_dpi;
    int y_dpi;
    const uint8_t *mono_bitmap;
    size_t bytes_per_row;
} m2022_page_t;

typedef struct {
    m2022_media_t media;
    m2022_quality_t quality;
    bool toner_save;
    int copies;
} m2022_job_options_t;

int m2022_encode_job(
    const m2022_job_options_t *options,
    const m2022_page_t *pages,
    size_t page_count,
    m2022_write_cb write_cb,
    void *ctx
);
```

The encoder must not know about:

- IPP;
- Bonjour;
- GUI;
- files;
- USB device discovery.

It only accepts raster pages + settings and produces printer-native bytes.

This separation is essential for testing.

# 13. Raster pipeline

The printer is monochrome, which simplifies the renderer significantly.

Possible internal representation:

```text
PDF / Apple Raster / PWG Raster
              │
              ▼
      grayscale 8-bit
              │
       scaling/crop
              │
    tone curve / density
              │
       halftone/dither
              │
              ▼
       1-bit page bitmap
              │
              ▼
         SPL/QPDL
```

## Initial quality modes

### Draft
- 600 dpi
- faster/simple dithering
- toner save

### Normal
- 600 dpi
- tuned monochrome conversion

### High
- 1200 dpi if confirmed stable
- higher-quality rasterization
- tuned small text / line-art handling

## Content optimization ideas

Future selectable modes:

- Auto
- Text
- Text + graphics
- Photo
- Line art

Potential knobs:

- gamma;
- black threshold;
- unsharp mask before binarization;
- ordered dithering;
- Floyd-Steinberg or other error diffusion;
- edge-preserving text threshold;
- density/toner bias;
- separate logic for vector/text-like versus photographic regions.

Do not optimize until a baseline encoder is proven physically correct.

# 14. “Better than the old driver” definition

The project should not claim a better driver just because it is newer.

Define measurable criteria.

## Compatibility

- works on current Apple Silicon macOS;
- survives OS upgrades with minimal dependencies;
- no ancient Samsung utility suite;
- iPhone/iPad printing;
- no custom client software;
- clean install/uninstall.

## Reliability

- 100 sequential one-page jobs without daemon crash;
- 20 multi-page jobs;
- printer unplug/replug recovery;
- Mac sleep/wake recovery;
- no duplicate Bonjour ghosts;
- no permanently wedged jobs after one malformed input.

## Quality

Create a physical test sheet containing:

- 4–12 pt text;
- serif/sans fonts;
- thin 1px/2px equivalent lines;
- diagonal lines;
- QR code;
- barcode;
- gray ramp;
- photograph;
- small reversed white-on-black text.

Compare:

1. old Samsung macOS driver;
2. SpliX baseline;
3. our pipeline.

Score visually and/or with high-resolution scans.

## Performance

Record:

- render latency;
- time-to-first-page;
- peak RAM;
- generated SPL job size;
- physical pages/minute where meaningful.

# 15. Preferred technology choices

## Stage A

Recommended:

### Core daemon
**Swift command-line executable** or **small C executable**.

Why Swift is attractive for Stage A:

- native macOS packaging;
- easy launchd integration;
- direct access to macOS frameworks;
- can call CUPS C APIs;
- can use DNS-SD/mDNSResponder APIs;
- easy future menu-bar UI.

Why C is attractive:

- CUPS and PAPPL are native C APIs;
- easiest migration toward PAPPL.

**Recommendation:** use Swift only if we want a polished macOS-native shell early. Otherwise use C from the beginning.

For a Codex-driven engineering project, **C + CMake** is likely the least surprising common denominator because Stage B strongly benefits from PAPPL.

## Stage B

Recommended:

- C17/C23 or C++20/23 core
- CMake
- PAPPL
- libcups
- mDNSResponder
- libusb only if PAPPL/device layer cannot handle what we need
- JBIG85 if required by chosen QPDL path

If reusing SpliX source directly, a C++ build becomes natural.

# 20. Security model

The first version is a **home-LAN appliance**, not a public server.

Rules:

1. bind/share only where needed;
2. default to local subnet;
3. do not expose CUPS administration to LAN;
4. do not enable Internet-facing NAT/port forwarding;
5. sanitize print-job filenames in logs;
6. bound job size;
7. bound concurrent jobs;
8. use temporary files safely;
9. remove temporary jobs after completion/failure;
10. treat all incoming print documents as untrusted.

When our own raster parser appears, fuzzing becomes important.

# 21. Reliability concerns

## Mac sleep

The Mac may stop advertising/responding while sleeping.

We cannot fix printing while the Mac is asleep unless wake-on-network behavior happens to help.

The desired behavior is:

- service survives wake;
- Bonjour record is restored;
- queue is healthy after wake;
- no manual restart.

## Printer power/offline

If the physical printer is off:

- AirPrint service can remain visible;
- printer state should ideally communicate stopped/offline;
- jobs should be queued or fail predictably;
- reconnect should recover.

## USB reconnect

USB device path may change.

Never key identity off a transient `/dev` style path.

Use USB IDs/device identity through CUPS or IOKit/libusb.

## Network changes

# 25. Decision records

## ADR-001 — Reuse working Samsung driver first

**Decision:** Stage A uses the existing macOS CUPS queue and Samsung driver.

**Reason:** We can prove the full iPhone → Wi-Fi → Mac → USB path before adding protocol reverse engineering.

**Consequence:** Stage A quality remains whatever the existing Samsung driver produces.

---

## ADR-002 — Standards-shaped client interface

**Decision:** Expose IPP + Bonjour/DNS-SD, AirPrint-compatible to iOS.

**Reason:** No client application is required and all Apple devices already understand the workflow.

---

## ADR-003 — Do not implement IPP from scratch

**Decision:** First use macOS CUPS; later use PAPPL.

**Reason:** IPP job semantics, capability negotiation, discovery, spooling, cancellation, printer state, and raster formats are already solved by mature projects.

---

## ADR-004 — Keep SPL/QPDL separate from networking

**Decision:** Native printer encoder is a narrow module consuming raster pages and producing bytes.

**Reason:** Makes it independently testable and lets us swap CUPS/PAPPL/network frontends.

---

## ADR-005 — Treat SpliX as reference/oracle before choosing code reuse

**Decision:** Do not immediately copy SpliX source into the project.

**Reason:** SpliX is GPL-2.0 and licensing should be intentional. Its supported M2020 implementation and SPL2 documentation are still extremely valuable for validation.

# 28. Main project risks

## Risk 1 — AirPrint discovery works but jobs fail

Cause:
- advertised document format does not match what CUPS can really process.

Mitigation:
- query capabilities;
- inspect incoming format;
- test PDF first;
- add explicit URF/PWG conversion only if necessary.

## Risk 2 — macOS printer sharing behavior changes

Mitigation:
- minimize undocumented hacks;
- use CUPS APIs and DNS-SD APIs;
- eventually migrate to a self-contained PAPPL Printer Application.

## Risk 3 — Old Samsung driver stops working after macOS update

Mitigation:
- exactly why Stage B exists;
- preserve captured native fixtures while the old driver still works.

## Risk 4 — Direct USB ownership conflicts

Mitigation:
- do not mix direct libusb access and active CUPS ownership casually;
- when Stage B starts, define a single owner of the physical device.

## Risk 5 — SPL/QPDL variants

Mitigation:
- exact hardware probe;
- SpliX M2020 reference;
- captured old-driver jobs;
- incremental hardware tests.

## Risk 6 — Licensing

Mitigation:
- keep SpliX outside the core initially;
- choose GPL-compatible project licensing if its code is incorporated;
- otherwise cleanly reimplement documented protocol behavior.
