# IPP Everywhere and AirPrint

Module `src/app/` (PAPPL system, driver data, callbacks). What clients see, what they send, and
what we learned making them happy. Measured 2026-09-02 on macOS 26.6.2 with PAPPL 1.4.12.

## What the printer advertises

DNS-SD: instance "Samsung M2022", type `_ipp._tcp` with sub-types `_print` and `_universal`
(the sub-type iOS browses for), on every interface. TXT record generated by PAPPL from our
driver data:

```text
txtvers=1 qtotal=1 rp=ipp/print ty=Samsung Xpress SL-M2022 product=(Samsung Xpress SL-M2022)
pdl=image/pwg-raster,image/urf,application/vnd.samsung-spl,image/jpeg,image/png
URF=V1.5,W8,PQ3-4-5,FN3,IS0-1-4,MT1-4-5-3,OB10,RS600
Color=F Duplex=F TLS=1.2 kind=document priority=0 mopria-certified=1.3
adminurl=http://<host>:8000/ UUID=<printer-uuid>
```

IPP (`ipptool -tv ipp://host:8000/ipp/print get-printer-attributes.test` passes):
`ipp-versions-supported 1.1,2.0`; `document-format-supported` as in `pdl`;
`pwg-raster-document-type-supported black_1,sgray_8`; `printer-resolution-supported 600dpi`;
`print-color-mode-supported auto,monochrome`; `sides-supported one-sided`; 14 media sizes with
12.5 pt margins; `media-default iso_a4_210x297mm`.

Checking discovery on macOS (`ippfind` was unreliable here; Apple's tool is definitive):

```sh
dns-sd -B _ipp._tcp,_universal local.        # instances carrying the _universal sub-type
dns-sd -L "Samsung M2022" _ipp._tcp local.   # the TXT record
```

## What clients send

| Client | Format | Raster | Notes |
|---|---|---|---|
| macOS 26 print path (CUPS `-m everywhere` queue, same as the print dialog) | `image/urf` (Apple Raster) | sGray 8-bit, 4960×7015 px at 600 dpi for A4 | With `RS300-600` advertised it rendered at **300 dpi for normal quality** and 600 dpi only for high; hence we advertise `RS600` only |
| Any client, PNG/JPEG | `image/png`, `image/jpeg` | PAPPL rasterises at 600 dpi sGray | scaled to fit the page |
| iOS / iPadOS | | | to be measured (M2 acceptance) |

Apple Raster jobs are streamed by PAPPL straight from the connection to our raster callbacks;
there is no spool file. The decoded page is what we capture (`server --capture DIR` writes
`job-NNN-pN.pgm`), and it is exactly the input our raster pipeline will get.

## Things that bit us

- **`print-color-mode=color` from a mono printer's clients.** Advertising `srgb_8` in
  `pwg-raster-document-type-supported` makes macOS's driverless PPD generator default to RGB and
  send `print-color-mode=color`, which PAPPL rejects for a monochrome driver. Advertise gray
  raster types only. Clients also send `auto`, so `print-color-mode-supported` must list `auto`
  and `monochrome`, as real mono AirPrint printers do.
- **Resolution follows print quality.** See the table: advertise only the engine resolution.
- **Page indices are 0-based** in PAPPL's `rstartpage`/`rendpage` callbacks.
- **PAPPL on Apple Silicon.** Its configure defaults to a universal binary; pin `-arch arm64`
  through CFLAGS/LDFLAGS (`scripts/build-pappl.sh`). CMake's `pkg_check_modules` mangles
  `-framework X`; we consume `pkg-config --libs --static pappl` ourselves.

## What this teaches

Discovery and capability negotiation are the whole user experience: the printer describes
itself once, in the TXT record and IPP attributes, and every client renders accordingly. Small
advertising mistakes (a colour raster type, an extra resolution) change what arrives on the
wire before a single line of our own rendering code runs.
